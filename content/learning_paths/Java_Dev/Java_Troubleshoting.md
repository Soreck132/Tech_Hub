| Problema | Descripción | Ejemplo | Resultado | Solución | Solución ejemplo |
|---|---|---|---|---|---|
| NullPointerException | Se utiliza un objeto cuyo valor es `null`. | `user.getAddress().getCity()` cuando `getAddress()` es `null`. | La operación falla con `NullPointerException`. | Identificar el objeto `null` mediante el stack trace y corregir su inicialización o validación. | `if (user.getAddress() != null) { user.getAddress().getCity(); }` |
| OutOfMemoryError | La JVM se queda sin memoria disponible en el heap. | Una colección continúa creciendo y mantiene millones de objetos. | La aplicación se vuelve lenta y eventualmente falla. | Analizar heap, GC y heap dump; corregir memory leak o consumo excesivo. | `jcmd <PID> GC.heap_info` y `jmap -histo <PID>`; después corregir la referencia que mantiene los objetos. |
| StackOverflowError | El stack de un thread se agota, normalmente por recursion infinita. | `process()` llama continuamente a `process()`. | El thread falla con `StackOverflowError`. | Corregir la condición de salida o reemplazar recursion por iteración. | `if (condition) { process(); }` agregando una condición de terminación válida. |
| ClassNotFoundException | Java no encuentra una clase que intenta cargar dinámicamente. | `Class.forName("com.mysql.jdbc.Driver")`. | La aplicación falla al cargar la clase. | Revisar dependencias, `classpath` y artifact desplegado. | `mvn dependency:tree` y agregar/corregir la dependencia requerida en `pom.xml`. |
| NoClassDefFoundError | Una clase requerida en runtime no está disponible correctamente. | La dependencia existe durante compilación pero no en producción. | La aplicación falla al cargar la clase. | Revisar dependency tree, `classpath`, artifact y versiones. | Ejecutar `mvn dependency:tree` y verificar que la dependencia esté disponible en runtime. |
| ConcurrentModificationException | Se modifica una colección mientras está siendo recorrida. | `for (String user : users) { users.remove(user); }` | Se genera una excepción durante la iteración. | Utilizar `Iterator.remove()` o `removeIf()`. | `users.removeIf(user -> user.equals("John"));` |
| Deadlock | Dos o más threads esperan recursos bloqueados entre ellos. | Thread A tiene Lock A y espera Lock B; Thread B tiene Lock B y espera Lock A. | Los threads quedan bloqueados indefinidamente. | Analizar thread dump y corregir el orden de adquisición de locks. | `jstack <PID>` y buscar `Found one Java-level deadlock`. |
| CPU alta | Un proceso Java consume una cantidad excesiva de CPU. | Un thread entra en un loop infinito. | La aplicación se vuelve lenta. | Identificar el proceso y thread que consume CPU. | `top -H -p <PID>` → identificar TID → `jstack <PID>` → localizar el thread problemático. |
| Runaway Java Process | Un proceso o thread continúa ejecutándose de forma anormal y consume recursos. | Un proceso ejecuta repetidamente una tarea sin condición de terminación. | CPU alta y degradación del servidor. | Identificar PID/thread, analizar logs y thread dump. | `ps -ef \| grep java` → `top -H -p <PID>` → `jstack <PID>`. |
| Garbage Collection excesivo | La JVM ejecuta GC frecuentemente intentando liberar memoria. | Old Generation permanece cerca del límite. | CPU alta, pausas y degradación del rendimiento. | Analizar GC, heap y objetos retenidos. | `jstat -gcutil <PID> 5s` y revisar si Old Generation permanece cerca de `100%`. |
| Memory Leak | Objetos que ya no son necesarios permanecen referenciados. | Un `HashMap` estático continúa acumulando objetos. | El heap crece continuamente y puede terminar en `OutOfMemoryError`. | Analizar heap dump e identificar referencias retenidas. | `jmap -dump:live,format=b,file=heap.hprof <PID>` y analizar el heap dump. |
| Thread Pool Exhaustion | Todos los threads disponibles están ocupados. | Muchos threads esperan respuestas de DB. | Nuevos requests quedan esperando o generan timeout. | Identificar qué mantiene ocupados los threads. | `jstack <PID>` y buscar múltiples threads en `WAITING`, `BLOCKED` o `TIMED_WAITING`. |
| Blocked Threads | Un thread espera un lock que otro thread mantiene. | Thread A espera un `synchronized block`. | Requests quedan bloqueados. | Identificar el lock y reducir la contención. | `jstack <PID>` → buscar `BLOCKED` y analizar el monitor/lock involucrado. |
| Connection Pool Exhaustion | Todas las conexiones disponibles hacia DB están ocupadas. | Queries lentas mantienen conexiones abiertas. | `Timeout waiting for connection`. | Revisar pool, queries y connection leaks. | Utilizar `try-with-resources`: `try (Connection c = dataSource.getConnection()) { ... }` |
| SQL lento desde Java | La aplicación tarda debido a una consulta SQL lenta. | `SELECT` realiza full table scan sobre millones de registros. | La API responde lentamente o genera timeout. | Revisar execution plan, índices, joins y locks. | `EXPLAIN` / Execution Plan → identificar scan costoso → agregar índice apropiado y validar nuevamente. |
| SQLException | Error relacionado con JDBC o la base de datos. | `SQLException: Connection refused`. | La operación contra DB falla. | Determinar si es conexión, autenticación, timeout, permisos o SQL. | Revisar logs y probar conectividad: `nc -vz <host> <port>`; después validar DB y credentials. |
| TimeoutException | Una operación no termina dentro del tiempo configurado. | Una API externa no responde dentro de 30 segundos. | La aplicación cancela la operación. | Identificar qué componente está causando el timeout. | Revisar logs por timestamp y correlation ID; medir DB/API response time antes de aumentar el timeout. |
| HTTP 500 | Error interno durante el procesamiento de una solicitud. | Una API genera `NullPointerException`. | El cliente recibe `500 Internal Server Error`. | Revisar logs, stack trace y correlation ID. | `grep -i "ERROR" application.log` → localizar stack trace → identificar `Caused by`. |
| HTTP 404 | El endpoint o recurso solicitado no existe. | `GET /api/users/123` apunta a una URL incorrecta. | El cliente recibe `404 Not Found`. | Validar URL, routing y deployment. | Probar endpoint con `curl`: `curl -i http://host/api/users/123`. |
| HTTP 401/403 | Problema de autenticación o autorización. | Token expirado o usuario sin permisos. | El cliente recibe `401` o `403`. | Revisar token, roles y permisos. | Validar `Authorization: Bearer <token>` y revisar roles/claims del usuario. |
| IllegalArgumentException | Un método recibe un argumento inválido. | `setAge(-5)`. | El método falla con una excepción. | Validar los inputs antes de ejecutar la operación. | `if (age < 0) throw new IllegalArgumentException("Age cannot be negative");` |
| NumberFormatException | Se intenta convertir un String inválido a número. | `Integer.parseInt("ABC")`. | La conversión falla. | Validar el input antes de convertirlo. | `try { Integer.parseInt(value); } catch (NumberFormatException e) { ... }` |
| Database Deadlock | Dos transacciones esperan recursos bloqueados por la otra. | Transaction A bloquea Row 1 y espera Row 2; B hace lo contrario. | Una transacción puede ser abortada por la DB. | Revisar locks, orden de operaciones y transacciones. | Consultar locks/deadlocks de la DB, identificar las transacciones involucradas y hacer que accedan a recursos en un orden consistente. |
| Application Slowdown | La aplicación sigue funcionando pero responde lentamente. | CPU, GC, DB o una API externa presentan degradación. | Aumenta el response time y pueden ocurrir timeouts. | Determinar el bottleneck antes de modificar configuración. | Revisar `top`, `jstat`, `jstack`, logs y métricas de DB para determinar dónde está la latencia. |
| Application Crash | El proceso Java termina inesperadamente. | `OutOfMemoryError` o proceso terminado por el sistema operativo. | El servicio queda indisponible. | Revisar logs, JVM errors y métricas del servidor. | `journalctl`, logs de aplicación y `dmesg`; identificar causa y reiniciar el servicio después de contener el incidente. |
| Log Error / Stack Trace | Los logs contienen información sobre una excepción o fallo. | `Caused by: SQLException...` | Permite identificar dónde y por qué ocurrió el problema. | Seguir el stack trace hasta la causa raíz. | `grep -i "Exception" application.log` → revisar `Caused by` → correlacionar timestamp y request ID. |
